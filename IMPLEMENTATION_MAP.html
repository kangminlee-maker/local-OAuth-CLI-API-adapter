Local OAuth CLI 애드온 구현 지도

이 문서는 로컬 OAuth CLI를 OpenAI·Anthropic 호환 API 표면으로 노출하는 설치형 프록시의 현재 구현 경계, 검증 기준, 남은 최적화 지점을 한눈에 정리합니다.

현재 목표

프록시는 실제 provider API와 같은 입출력 표면을 보여야 하지만, 런타임에서는 direct provider API를 호출하지 않아야 합니다. direct API는 명시적인 비교 벤치마크, 기준 답변 생성, 품질 판정에만 사용합니다.

proxy-codex의 OpenAI Chat 장애 보고서 의미 품질은 타임라인 보존 규칙 이후 95점 기준을 통과했습니다. 이미지 b64_json 생성은 단일 요청 품질 보강과 n>1 병렬 실행을 반영했습니다. 남은 큰 병목은 이미지 스트리밍 첫 완성 이미지 지연과 더 넓은 semantic suite 반복 검증입니다.

런타임 흐름

1. API 수신 startLocalApiProxy가 OpenAI Chat, OpenAI Responses, OpenAI Images, Anthropic Messages 호환 요청을 받습니다.
2. 요청 정규화 provider별 입력을 내부 메시지, 도구, 이미지 참조, 응답 형식, 스트리밍 모드, effort, verbosity로 변환합니다.
3. 로컬 CLI 실행 OpenAI 표면은 CodexAppServerBackend, Anthropic 표면은 ClaudeCodeBackend로 보내며, 자식 프로세스는 provider API 키를 받지 않습니다.
4. 응답 재구성 텍스트, 도구 호출, SSE delta, provider token usage, 이미지 응답을 원래 API 스키마에 맞춰 반환합니다.

벤치마크 해석

영역 현재 판단 다음 의미
OpenAI 텍스트·도구 속도 proxy-codex는 대부분 direct 대비 1.2배에서 2.7배 느립니다. Responses 도구 스트리밍의 firstToolArgumentMs는 arguments-only fast path 후 direct 대비 169.7%로 줄었지만, non-stream 도구 호출은 이번 3회에서 201.9%로 악화되었습니다. 도구 wrapper 파싱 지연은 줄었고, 남은 병목은 Codex app-server turn 내부의 첫 delta 및 tail latency입니다. firstData는 조기 SSE 이벤트 때문에 빠르게 보이므로 사용자 체감 지표로 쓰지 않습니다.
Anthropic 텍스트·도구 속도 proxy-claude는 direct Opus 대비 대체로 1.1배에서 2.3배 느립니다. 중앙값은 OpenAI proxy보다 안정적이지만, 멀티모달과 스트리밍 꼬리 지연을 계속 분리 계측해야 합니다.
의미 품질 OpenAI Chat realistic semantic suite는 최종 10/10 통과했습니다. OpenAI Responses는 전체 suite 재측정에서 18/20이었고, 남은 두 케이스는 일반 규칙 보강 후 각각 95점, 96점으로 targeted closure 통과했습니다. 타임라인 체크포인트, proxy/direct 영향 범위, 조건-결과 연결, 부정 제약, provider error shape, 한국어 incident 문체를 일반 규칙으로 유지하고 3회 반복 suite로 안정성을 다시 확인해야 합니다.
