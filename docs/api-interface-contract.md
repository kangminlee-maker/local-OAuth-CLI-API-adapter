# API interface contract

이 문서는 local OAuth CLI API adapter가 외부에 제공하는 input/output interface 규약이다. 원칙은 명확하다.

- 구현된 surface의 input spec과 output spec은 OpenAI 또는 Anthropic API-compatible shape를 기준으로 한다.
- provider와 동일하게 보이도록 simulate한 subset만 public contract로 본다.
- 구현상 provider와 다르게 처리하는 영역은 "구현 차이와 제약"에 별도 명시한다.
- 런타임 proxy는 direct provider API를 호출하지 않는다. direct provider API는 benchmark, reference 생성, 별도 direct transport 설계에서만 다룬다.

## Supported surfaces

| Provider-compatible surface | Endpoint | Runtime backend |
| --- | --- | --- |
| OpenAI Models | `GET /v1/models` | local backend metadata |
| OpenAI Chat Completions | `POST /v1/chat/completions` | Codex-compatible local backend |
| OpenAI Responses | `POST /v1/responses` | Codex-compatible local backend |
| OpenAI Images | `POST /v1/images/generations`, `/v1/images/edits` | Codex image-generation backend for every live direct image model name |
| Anthropic Messages | `POST /v1/messages` | Claude-compatible local backend |

## OpenAI Chat Completions

### Input spec

The request body is a JSON object compatible with Chat Completions for the implemented subset. **Its top-level schema is the direct
API's own, measured 2026-08-30 on `gpt-5.6-terra` (`docs/conformance-matrix.md` §5.5.5)**: a key outside the set below is 400
`unknown_parameter`, every accepted key is validated with the direct API's envelope (status, type, param, code, message), and a body
with two faults is answered about the same one the direct API answers about — required parameters first (`model`, then `messages`),
then unknown keys, then the fields in a **measured** order that is neither alphabetical nor one position per key (the value a model
family refuses is checked in a later pass than the field's type: `stop` is reported before `temperature: 0.5` and after
`temperature: 'x'`). The order and the pairs that pin it are in `docs/conformance-matrix.md` §5.5.5; nothing beyond those pairs is
claimed.

Re-check it with `pnpm e2e:text:parity`, which sends each of these bodies to this proxy and to the direct API and compares the two
answers field by field; `pnpm probe:text-surface-keys` is the instrument the table was measured with.

| Field | Supported shape | Handling |
| --- | --- | --- |
| `model` | string | **Required**, as on the direct API. Absent, empty, whitespace-only: 400 `you must provide a model parameter` with **no `param` and no `code`** — Chat's own sentence, which differs from Responses' `missing_required_parameter`. A non-string is `invalid_type`. Whether it selects the executed model depends on `modelSelection.honorRequestModel`; see Model execution. |
| `messages` | array | **Required** and non-empty: absent is `missing_required_parameter` (reported before any unknown key), `[]` is `empty_array`, a non-array is `invalid_type`, and a non-object member is `invalid_type` naming `messages[i]`. |
| `messages[].role` | `system`, `developer`, `user`, `assistant`, `tool`, `function` (deprecated) | **Required** — it discriminates the message schemas. Missing: `missing_required_parameter`. Unknown: `invalid_value` listing the six in the direct API's own order. Never a silent rewrite, which turned a typo'd `assistantt` into a user turn. |
| `messages[].content` | string or content-part array | **Required on every role**, re-measured 2026-08-31 on three model families with a positive control: an absent or `null` `content` is 400 with param `messages.[i].content` (the dotted-bracket form this fault alone uses), no `code`, and `Invalid value for 'content': expected a string, got null.` An empty string and an empty array ARE content and are accepted. The one exemption is the assistant schema's own — a `tool_calls`, `function_call`, `refusal` or `audio` member stands in for it. Required-ness is the LAST check of all; a defined value of another type is `invalid_type` naming `messages[i].content`, at the `messages` position. This row said "Optional on every role" until 2026-08-31; see §5.5.5-A for how the instrument produced that reading. Text is flattened; `image_url` parts are read as images. |
| `messages[].tool_calls` | assistant tool call array | Flattened into conversation context for tool-result continuation. |
| `messages[].tool_call_id` | string | Preserved for `tool` role messages. |
| `messages[].name`, `messages[].refusal` | string | Accepted and not read, as on the direct API — neither side reports them back. |
| `tools` | OpenAI function tool array | `tools[i].function` and `tools[i].function.name` are required (`missing_required_parameter`); a non-array is `invalid_type`. `function.name`, `function.description` and `function.parameters` are preserved. |
| `tool_choice` | `none`, `auto`, `required`, or `{ type: "function", function: { name } }` | Mapped to internal tool-choice modes. A string outside the three modes is `invalid_value` with the list; an object must carry `function` and then `function.name` (`missing_required_parameter`) **whatever its `type` says**; another type is `invalid_type`. Unknown values no longer fall back to `auto`. |
| `functions`, `function_call` | deprecated arrays/objects | Validated as the direct API validates them (`functions[i].name`, `function_call.name` required) and **not applied**: mapping them onto `tools` would run the tools but answer in the modern shape, and a legacy client reads `message.function_call`. |
| `stream` | boolean | `true` enables SSE chunks; a non-boolean is `invalid_type`. |
| `stream_options.include_usage` | boolean | Emits final usage chunk when true. |
| `stream_options.include_obfuscation` | boolean | Defaults to true unless explicitly false. An unknown member of `stream_options` is `unknown_parameter` naming `stream_options.<key>`. |
| `response_format` | `{ type: "text" \| "json_object" \| "json_schema" }` | `type` is required (`missing_required_parameter` on `response_format.type`) and enumerated (`invalid_value` with the three). A `json_schema` format must carry `json_schema` and its `name`, both `missing_required_parameter` when absent — the proxy used to accept `{type:"json_schema"}` alone and run the turn in JSON mode with no schema, which is structured output the caller asked for and never got. `json_object` and `json_schema` enable JSON mode/schema steering; the `json_schema` name and `strict` are preserved. |
| `reasoning_effort` | `none`, `low`, `medium`, `high`, `xhigh` | This model family's set, measured. **`minimal` and `max` are outside it** and get the direct API's `unsupported_value` with the supported list, as does any other value — including a non-string, which the message renders Python-style exactly as the direct API does. |
| `verbosity` | `low`, `medium`, `high` | Forwarded when the caller sends one; nothing is sent when they do not. An out-of-enum value is `invalid_value` with the list. |
| `max_completion_tokens` | integer >= 1 | Passed to the backend as the max-token hint. Below 1 is `integer_below_min_value`. |
| `max_tokens` | — | **Refused**: `unsupported_parameter`, `Use 'max_completion_tokens' instead.` — the direct API's own answer for this family. |
| `stop`, `logit_bias`, `prediction` | — | **Refused** with `unsupported_parameter`, whatever the value: this model family refuses all three on the direct API, so there is nothing to realize. |
| `frequency_penalty`, `presence_penalty` | number -2..2 | Out of range is `decimal_above_max_value` / `decimal_below_min_value` with the bound. **Refused with `unsupported_parameter` while the model reasons** (any `reasoning_effort` but `none`, including the default) and accepted at `reasoning_effort: none` — both measured. Accepted here means accepted and **not applied**: no local runtime samples with a penalty. |
| `logprobs` | boolean | Same rule as the penalties: refused while the model reasons, accepted and not applied at `reasoning_effort: none` — the response carries no `logprobs`, where the direct API's does. |
| `top_logprobs` | integer 0-5 | Three measured envelopes: below 0 is `integer_below_min_value`, above 5 is a bare 400 (`must be less than or equal to 5`, no code), and without `logprobs: true` it is the direct API's own sentence. Not applied. |
| `n` | integer 1-8 | Validated as the direct API validates it — the ceiling of **8** is measured, not assumed — and realized as n backend turns, one per returned choice. See the `n` row under Implementation differences for what that costs and how usage is reported. |
| `temperature` | number | Only the default `1` is accepted (null is omission). A non-number is `invalid_type`; any other number is 400 / `param: temperature` / `code: unsupported_value` — the direct API's own envelope for this family, since no backend applies the value. |
| `top_p` | number | Only the default `1` is accepted (null is omission). A non-number is `invalid_type`; any other number is `unsupported_parameter`. |
| `service_tier` | `auto`, `default`, `fast`, `flex`, `priority` | Validated against the direct API's own list, and echoed as the direct API echoes it — which is **not the request**: `fast` and `priority` both come back as `priority`, `flex` as `flex`, and `auto`, `default` and an omitted value as `default`. The same resolution applies on `/v1/responses`, which validates the field for the same reason (its value is echoed). |
| `metadata` | map | At most 16 properties, keys at most 64 characters, string values at most 512 — each with its own measured code. Accepted and not applied. |
| `prompt_cache_retention` | `24h` | `in_memory` is refused with the direct API's sentence (`This model is compatible only with 24h extended prompt caching`); `24h` is accepted and not applied. |
| `prompt_cache_options` | `{ ttl, mode }` | The object and its member names are validated — an unknown member is `unknown_parameter` naming `prompt_cache_options.<key>`. Accepted and not applied. |
| `moderation` | `{ model, … }` | `moderation.model` is required, as on the direct API. Accepted and **not applied**: the local runtimes moderate nothing, so the response carries no `moderation` object where the direct API's does. |
| `store`, `user`, `safety_identifier`, `seed`, `prompt_cache_key`, `parallel_tool_calls` | per the direct schema | Type-validated and accepted without effect. None of them appears in a Chat response, so nothing is echoed as applied. |
| `audio`, `modalities`, `web_search_options`, `reasoning`, `text` | — | **Unknown parameters**, as on the direct API. `reasoning.effort` and `text.verbosity` used to be accepted here as alternate spellings of `reasoning_effort`/`verbosity`; a body the direct API refuses no longer succeeds against this proxy. |

### Output spec

Non-streaming response uses OpenAI Chat Completions shape:

```json
{
  "id": "chatcmpl-...",
  "object": "chat.completion",
  "created": 0,
  "model": "...",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "...",
        "refusal": null,
        "annotations": []
      },
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 0,
    "completion_tokens": 0,
    "total_tokens": 0,
    "prompt_tokens_details": {
      "cached_tokens": 0,
      "audio_tokens": 0
    },
    "completion_tokens_details": {
      "reasoning_tokens": 0,
      "audio_tokens": 0,
      "accepted_prediction_tokens": 0,
      "rejected_prediction_tokens": 0
    }
  },
  "service_tier": "default",
  "system_fingerprint": null
}
```

When the backend returns tool calls, `message.content` is `null`, `message.tool_calls` is populated, and `finish_reason` is `tool_calls`.

### Streaming output spec

SSE stream uses `data: ...` Chat Completions chunks and ends with `data: [DONE]`.

- First assistant chunk includes `delta.role`.
- Text chunks include `delta.content`.
- Tool chunks include `delta.tool_calls[].function.arguments` deltas.
- Final choice chunk has `finish_reason: "stop"` or `"tool_calls"`.
- If `stream_options.include_usage` is true, an extra chunk with `choices: []` and `usage` is emitted before `[DONE]`.
- Chunk `usage` is `null` when `include_usage` is true and the chunk is not the final usage chunk.

## OpenAI Responses

### Input spec

The request body is a JSON object compatible with Responses for the implemented subset.

| Field | Supported shape | Handling |
| --- | --- | --- |
| `model` | string | **Required**, as on the direct APIs. Absent, empty, whitespace-only, or non-string values return 400 `invalid_request_error` with `param: model`. Whether it selects the executed model depends on `modelSelection.honorRequestModel`; see Model execution. |
| `instructions` | string | Added as system-level instruction input. |
| `input` | string or array | String becomes a user message. Array items must be objects (a primitive is 400). Items are polymorphic as on the direct API: a message item — no `type`, or `type: "message"` — requires a `role` in `system`/`developer`/`user`/`assistant` (missing or unknown is 400 with `param: input[i].role`); typed items (`function_call`, `function_call_output`, ...) have no role and need none. |
| `input[].role` | `system`, `developer`, `user`, `assistant` | **Required on message items** (no `type`, or `type: "message"`); missing or unknown is 400 with `param: input[i].role`. Typed items (`function_call`, `function_call_output`, ...) have no role and need none. An item `type` that is not a string is 400; unknown *string* types are deliberately not rejected — the direct item union grows with the API, and pinning it here would 400 tomorrow's valid items. |
| `input[].content` | string, object, or content-part array | Text is flattened. `input_image` parts are preserved as image inputs. |
| Replayed typed items | `function_call`, `function_call_output`, `reasoning`, everything else | A `function_call` / `function_call_output` pair is replayed as this proxy's own tool history and reaches the `codex-backend` transport as native `function_call` / `function_call_output` items. A `reasoning` item replays as **nothing**: its `summary`, `reasoning_text` and `encrypted_content` have no slot in either runtime, and putting them in a turn told the model its own chain of thought in the user's voice. Every OTHER typed item — the hosted-tool calls and outputs a client replays `output` as `input` to preserve — reaches the model as a labelled transcript record (`[replayed item]`, the item `type`, then the item's JSON) in the turn's own role. It is **not** replayed as a function tool result: it has no `call_id` this runtime issued, and writing it as one made the default transport parse it back into an empty `function_call_output` under an invented id, so the record's own result never reached the model. Nothing parses the label back, so text inside a record cannot forge a tool-result boundary. |
| `tools` | function tools | Same tool parser as Chat Completions. |
| `tool_choice` | string or object | Preserved in output response config and mapped to internal tool-choice mode. |
| `stream` | boolean | `true` enables Responses SSE events. |
| `stream_options` | `{ include_obfuscation }` | This surface's member set is `include_obfuscation` alone. `include_usage` is a Chat key and **unknown here** — 400 `unknown_parameter` `stream_options.include_usage` (measured 2026-08-30); this proxy used to accept it as an extension. |
| `text` | `{ format, verbosity }` | The member set is closed (`text.zzz` is 400 `unknown_parameter`). `format.type` is `json_object`, `text` or `json_schema` — that order, which is not Chat's — and a `json_schema` format without `format.name` is 400 `missing_required_parameter` `text.format.name`. Faults here are reported at `text`'s slot, ahead of every later field and of the model-capability pass. |
| `text.verbosity` | `low`, `medium`, `high` | Forwarded when sent, omitted when not. Outside the enum it is 400 `invalid_value` `text.verbosity` — the direct API's envelope, not a sentence of this proxy's. |
| `reasoning.effort` | `none`, `low`, `medium`, `high`, `xhigh`, `max` | Two layers, both measured: outside the SCHEMA set (`none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`) it is 400 `invalid_value`; inside it but outside what this model family runs — which is `minimal` — it is 400 `unsupported_value` naming the model. `max` is accepted here and refused on Chat, and runs at the backends' highest effort. An integer and any other non-string each get their own type sentence. Request value takes priority over fallback settings. |
| `max_output_tokens` | integer >= 16 | Passed to backend as max token hint. The floor is **16**, not 1 (measured at 1, 15 and 16): below it, 400 `integer_below_min_value`. |
| `temperature` | number | Only the default `1` is accepted (null is omission). Any other value is 400 `invalid_request_error` / `param: temperature` / `code: null`, message `Unsupported parameter: 'temperature' is not supported with this model.` — the direct API's envelope on this surface. The response object echoes `temperature: 1` — the direct API's own default, not the caller's value. |
| `top_p` | number | Rejected whenever present and non-null, at any value including `1`: 400 `invalid_request_error` / `param: top_p` / `code: null` (the direct Responses API refuses the parameter outright on this model family). The response object echoes `top_p: 0.98`, which is what the direct API echoes when the parameter is absent — the only state it can be in here. |
| `previous_response_id`, `conversation`, `prompt` | ids of server-side state | This proxy stores none of it, so **every** id is unknown and every one of these requests is refused with the direct API's own answer: `previous_response_id` 400 `previous_response_not_found`, `conversation` and `prompt` 404 with no `param`, and the two mutually exclusive ones 400 `mutually_exclusive_parameters`. They are a PHASE, not field positions — every schema fault beats them and they beat the model-capability pass — and among themselves the order is `conversation`, `prompt`, `previous_response_id`. The alternative, which is what this proxy used to do, was to echo the id back and run the turn with no prior context at all. To continue a conversation, feed the previous response's `output` items back in `input`; that round trip is checked by a test. |
| `input[]` items | message or typed item | Strict, at the `input` slot: an item that is not an object is `invalid_type`; a `type` outside the direct union is `invalid_value` naming all 33; a message item's `role` must be `assistant`/`system`/`developer`/`user` and its `content` is required; unknown members are `unknown_parameter`. `phase` is the ASSISTANT item's own member (`commentary`/`final_answer`) and is refused on any other role — which is what makes this proxy's own `output` valid as input. Content blocks are checked twice: outside the whole union names `content[N].type`, inside it but outside this role's variant names `content[N]`. |
| `tools[]` items | objects | `type` is required; a `function` tool requires a top-level `name`. The Responses tool shape is flat — a Chat-shaped `{type:'function', function:{name}}` is 400 `missing_required_parameter` `tools[0].name` here, as on the direct API. A nameless function tool used to be run under the invented name `tool`. |
| `prompt_cache_key`, `safety_identifier`, `metadata`, `user`, `store`, `truncation` | provider-style fields | Reflected in the response object. |
| Responses accepted-and-not-applied keys | `background`, `parallel_tool_calls`, `max_tool_calls`, `truncation`, `store`, `include`, `context_management`, `metadata`, `user`, `safety_identifier`, `prompt_cache_key`, `prompt_cache_options` are validated as the direct API validates them and have no effect on the turn. Unlike Chat, this surface HAS echo fields for several of them, and those echoes report **the request, not the run** — a `parallel_tool_calls: false` in the response says what was asked for, not what the backend did. `include` and `context_management` are not echoed at all, which is also what the direct API does (measured 2026-08-31; §5.5.6's first draft said otherwise). `background: true` returns a completed response rather than a pollable job — there is no job store here and `GET /v1/responses/{id}` is a 404. | The option rules' third case: no slot on the runtime, nothing to realize in code, and the direct API accepts them. Echoing the request is the direct API's own behaviour, so the echo stays and the non-effect is stated here instead — the same shape as the Chat and Anthropic rows. |

### Output spec

Non-streaming response uses Responses object shape:

```json
{
  "id": "resp_...",
  "object": "response",
  "created_at": 0,
  "status": "completed",
  "background": false,
  "billing": { "payer": "developer" },
  "completed_at": 0,
  "error": null,
  "instructions": null,
  "max_output_tokens": null,
  "model": "...",
  "output": [],
  "parallel_tool_calls": true,
  "reasoning": {
    "context": "current_turn",
    "effort": "medium",
    "summary": null
  },
  "service_tier": "default",
  "store": true,
  "temperature": 1,
  "text": {
    "format": { "type": "text" },
    "verbosity": "medium"
  },
  "tool_choice": "auto",
  "tools": [],
  "usage": {
    "input_tokens": 0,
    "output_tokens": 0,
    "total_tokens": 0,
    "input_tokens_details": { "cached_tokens": 0 },
    "output_tokens_details": { "reasoning_tokens": 0 }
  }
}
```

Text output is represented as an assistant message item with `content[].type: "output_text"`. Tool output is represented as `function_call` items with `call_id`, `name`, and `arguments`. A `reasoning` item leads the array when — and only when — the backend opened one at the head of the turn, carrying the id the backend gave it; a turn the runtime answered without reasoning has no such item, and neither does one whose backend opened it after the turn had already produced output (the completed body places the item by rule and the stream by arrival, so only the leading item can be reported the same way on both). Reporting it at all is per-runtime: the `codex-backend` transport reads it from the backend's own stream, while the `claude` runtime and the `app-server` transport do not surface reasoning items, so their responses carry none even where `usage.output_tokens_details.reasoning_tokens` is non-zero. The rest of the array is ordered the way the turn was produced: a call made before any narration precedes the message item.

### Streaming output spec

Responses streaming uses named SSE events:

- `response.created`
- `response.in_progress`
- `response.output_item.added`
- `response.output_item.done`
- `response.content_part.added`
- `response.output_text.delta`
- `response.output_text.done`
- `response.content_part.done`
- `response.function_call_arguments.delta`
- `response.function_call_arguments.done`
- `response.completed`
- `error`

Each event payload includes a monotonically increasing `sequence_number`. The stream ends at its terminal event — `response.completed`, or `response.incomplete` for a turn cut off at its output limit — with no `data: [DONE]` sentinel: the vendor sends none (captured 2026-08-29), and a frame that is not a Responses event is one a strict SDK has to skip or reject. A turn that fails mid-stream is the one exception: an in-band `error` event followed by `data: [DONE]`, a shape the direct API's failure path has not been captured for (**unmeasured**).

A `reasoning` item, when the backend reports one, is announced first — `response.output_item.added`/`.done` at `output_index: 0` — ahead of the message item and of every `function_call`, and it is the first output item a client sees. A turn whose runtime reported no reasoning item announces none.

## OpenAI Images

### Input spec

Images requests accept JSON bodies; edits also accept `multipart/form-data`. There is no `/v1/images/variations`: the direct API removed it with `dall-e-2` (404, measured 2026-08-29), and this proxy answers 404 too.

**Model namespace (2026-08-29).** `model` is required and must be one of the image models the direct API serves — `gpt-image-1`, `gpt-image-1-mini`, `gpt-image-1.5`, `gpt-image-2`, `gpt-image-2-2026-04-21`, `chatgpt-image-latest` (its `GET /v1/models`, 2026-08-29). Every one of them runs on the local Codex image backend, whose image model is `gpt-image-2-codex`; the name selects nothing but its own validation. `dall-e-2` and `dall-e-3` no longer exist there and are refused here with the direct envelope; so is the proxy's former invented route name `image-2` — use `gpt-image-2`.

| Field | Generation | Edit | Handling |
| --- | --- | --- | --- |
| `model` | required | required | Absent: 400 `invalid_request_error` / `model` / `missing_required_parameter`. Null or non-string: 400 `invalid_type` naming the JSON type (`got null instead`, `got an integer instead`). Any name outside the list above, the empty string included: 400 `image_generation_user_error` / `model` / `invalid_value`, `The model '<name>' does not exist.` — all three measured. |
| `prompt` | required | required | Absent: 400 `missing_required_parameter`; non-string (null included): 400 `invalid_type` naming the JSON type; empty string: 400 `empty_string` (`Invalid 'prompt': empty string. Expected a string with minimum length 1, but got an empty string instead.`); a whitespace-only prompt is accepted and runs (all measured 2026-08-30). At most 32,000 UTF-16 code units. |
| `images` (JSON) / `image`, `image[]` (multipart) | invalid | required | A JSON edit names its images as `images`, an array of objects (`{image_url}` with a URL or data URL, `{b64_json}`, `{file_id}`); `image` or `image[]` in JSON is 400 `invalid_value` with the direct pointer (`use 'images' (array)`), a non-array or null `images` is 400 `invalid_type` naming what it got, a non-object member is 400 `invalid_type` on `images[i]`, an empty array is 400 `empty_array`, an absent `images` is 400 `missing_required_parameter`. Multipart names its files `image` or `image[]`; a multipart part named `images` is 400 `invalid_value` with the direct pointer (`For multipart/form-data use 'image' or 'image[]'.`). On a generation `images` is an unknown parameter (400 `unknown_parameter`). |
| `mask` | invalid | optional | On a generation an unknown parameter (400 `unknown_parameter`, measured). On an edit, sent to the backend as the `image_generation` tool's `input_image_mask` (a data URL for base64/path sources, the URL itself for URL sources); never attached as an input image; null is omission. On the diagnostic `app-server` image transport, which has no tool declaration, the mask is composited in code on the returned image — see the "Images `app-server` transport" row. |
| `n` | optional | optional | Integer 1-10, default 1; null is omission. Out of range: 400 `integer_below_min_value` / `integer_above_max_value` (`Invalid 'n': integer below minimum value. Expected a value >= 1, but got 0 instead.`); a decimal, string or boolean in JSON: 400 `invalid_type` naming the type (`a decimal number`, `a string`, `a boolean`). In multipart a digit string is the integer it spells and anything else is 400 `invalid_type` `expected an integer, but got a string value that could not be converted into an integer` (measured). |
| `size` | optional | optional | `auto` or `WIDTHxHEIGHT`, both divisible by 16; null is omission; a non-string is 400 `invalid_type` (`expected a string, but got an integer instead`). Any other string is 400 `image_generation_user_error` / `size` / `invalid_value`: `Invalid size 'bogus'. Expected WIDTHxHEIGHT, for example '1824x1024'.` (also for `0x0`), or `Invalid size '9x9'. ### Output spec

Non-streaming output follows Anthropic Messages shape:

```json
{
  "id": "msg_...",
  "type": "message",
  "role": "assistant",
  "model": "...",
  "content": [
    {
      "type": "text",
      "text": "..."
    }
  ],
  "stop_reason": "end_turn",
  "stop_sequence": null,
  "usage": {
    "input_tokens": 0,
    "output_tokens": 0
  }
}
```

When tool calls are returned, `content` contains `tool_use` blocks and `stop_reason` is `tool_use`. Text and `tool_use` blocks appear in the order the model produced them, the same order the stream opened its content blocks in. Tool arguments are published as the bytes the runtime wrote, whitespace included — on this surface `input` is a JSON value, not a string, and the body splices the bytes in rather than parsing and re-serializing them (round 21: a round trip had published `9007199254740993` as `…992` and `1e999` as `null` while the stream carried the bytes). A call whose arguments are not a JSON object — bytes that are not JSON, JSON that is not an object, or a wrapper `arguments` member that is not a string — is refused (502) on the wrapper backends, forced or not; nothing is repaired into `{ "input": "..." }` any more (round 18). The one exception is a call the runtime reports as cut off by its output limit: it is delivered as the fragment it is. The direct API projects it as the complete members parsed so far in the body and the verbatim fragment in a stream block that is never closed (measured 2026-09-04, `review-artifacts/stage2/report.md` M6, for an object cut mid-member), and since round 19 so does this proxy: the body carries `completeTopLevelMembers` of the fragment, the stream the fragment with no `content_block_stop` — for the turn's final BLOCK (the last call, with no narration or call after it), and only when its bytes are not a whole JSON object; a last call whose bytes are a complete object under the limit is closed like any other, the direct API's answer for that shape being unmeasured (r23-codex), then `message_delta` with `stop_reason: "max_tokens"`.

### Streaming output spec

Anthropic streaming uses named SSE events:

- `message_start`
- `content_block_start`
- `content_block_delta`
- `content_block_stop`
- `message_delta` — carries the whole usage, not only `output_tokens`. `message_start` is written before the runtime has reported anything, so its counts are zeros; this is the first event that knows the real ones, and the input and cache counts would otherwise never reach a streaming client.
- `message_stop`
- `error`

Text deltas use `delta: { "type": "text_delta", "text": "..." }`. Tool input deltas use `delta: { "type": "input_json_delta", "partial_json": "..." }`.

## 구현 차이와 제약

This section is the explicit list of areas where implementation intentionally differs from a full direct OpenAI or Anthropic API.

| Area | Difference | Reason / expected behavior |
| --- | --- | --- |
| Runtime authority | Proxy runtime never calls direct provider APIs. | Local OAuth CLI auth is the product boundary. Direct provider calls belong only to benchmark/reference/direct-transport surfaces. |
| Codex text/tool transport | Default `codex-backend`; `app-server` remains available as a diagnostic transport. | The product proxy is hybrid: provider-compatible text/tool requests and the Images API use `codex-backend` (the Images route through its `image_generation` tool; `--codex-image-transport app-server` is the diagnostic alternative), while native local chat uses Codex app-server. `codex-backend` calls ChatGPT Codex backend with the local Codex OAuth token and maps native Responses SSE text/function-call events back to the public proxy schema. It is not a direct OpenAI Platform API call. It refreshes access tokens through the Codex OAuth refresh endpoint and asks the user to re-authenticate only when the refresh token is expired, revoked, or already used. |
| Chat tools with model-default reasoning | gpt-5.6-family models reject `/v1/chat/completions` requests that carry function tools without `reasoning_effort: 'none'` (400, "use /v1/responses or set reasoning_effort to 'none'"). The proxy accepts such requests and runs them, because its Codex backend path translates chat requests to the Responses surface, where tools and reasoning coexist. | Deliberate leniency, kept as a documented proxy-enhanced behavior (decided 2026-08-19). Clients that must stay portable to the direct API should send `reasoning_effort: 'none'` with chat tools on 5.6-family models; benchmark provider-parity rows do. |

Omitting `--setting-sources` is NOT equivalent to the empty value: probed on 2.1.235, an omitted flag loads user settings exactly as `user` does. The startup banner reports the effective state and why. | Changed 2026-08-29; the default previously loaded the `user` source. It also ran the operator's hooks — arbitrary local commands — once per turn, for any local client that could reach the port. Measured 2026-08-19 at ~3.1k tokens and ~1s per message; a paired benchmark on 2026-08-28 showed the claude arm running 203 characters longer than its direct reference with the bundle loaded. |
| Tools on a continuation turn | Tools stay available for every turn of a conversation, including the one that follows a `tool_result`: the runtime is asked for the same decision shape there, so it can either answer or call another tool. A client that wants its OWN `response_format` / `text.format` schema honoured on such a turn takes the tools off that turn with `tool_choice: "none"` — on `/v1/messages` too, where that combination used to be refused outright. Two consequences a client owns: the tool catalogue is serialized into every turn's prompt, not just the first, which the caching row's numbers are paid against; and nothing here ends a tool conversation, so a client that relied on the continuation being forced into a final answer now needs its own limit on rounds. | The continuation used to be given plain-text mode, on the reading that it is where the model finally answers. Measured on the claude runtime before and after; the answer case still returns `end_turn` with text, because the decision shape carries it. |
| Prompt caching | The proxy implements no caching of its own and holds no conversation state — each request replays the whole conversation. What `usage` reports is the cache the RUNTIME achieved against its provider, mapped into the shape the client asked in: `cached_tokens` inside `prompt_tokens` on the OpenAI shapes, and `cache_read_input_tokens` outside `input_tokens` on `/v1/messages`. Client-supplied `cache_control` is accepted and ignored. | The two runtimes cache differently and the difference is visible. Measured 2026-08-27 on a growing conversation: the codex runtime's provider caches prefixes automatically, so replay is exactly what it wants — 7,936 of 8,360 prompt tokens served from cache by the third turn. | Text alongside tool calls | A turn that narrates and then calls a tool returns both, on every surface and in both modes: chat `content` carries the narration next to `tool_calls`, while the ordered surfaces report them in the order the model produced them — Responses `output` and `/v1/messages` `content` put the narration first when it came first, and the `function_call` / `tool_use` blocks first when the call did. The order is the order the client was TOLD: a call the vendor identifies only after narration that followed it (the protocol names a call on its first frame; **unmeasured**) is announced after that narration on the stream, and the body reports the same order rather than the backend's positions (declared; round 28). Chat is unordered by shape (`content` and `tool_calls` are separate fields), so nothing there depends on it. | Both upstream APIs return them together, and the streamed deltas already delivered the narration — dropping it from the result made streaming and non-streaming clients disagree about what the model said. A fixed order was the same disagreement in a subtler form: the stream opened the tool block first and the completed body then claimed the text came first. |
| Tool turns stream at completion (`claude`, `app-server`) | A turn with `tools` releases nothing — not even the stream's opening frames — until the runtime has finished and the completed answer has been read; the stream is then a projection of that one reading, and a refused turn is an HTTP 502 on the stream as on the buffered body. Plain text turns and the `codex-backend` transport stream live. | The wrapper had two readers — an incremental walk for the stream and `JSON.parse` for the body — and on malformed output they disagreed, so a streaming client could execute a call the body denied; a released byte cannot be retracted. Measured 2026-09-04: no cost on `claude`, whose wrapper already arrived whole in `structured_output`; about 0.3 s later call announcement per turn on `app-server`. |
| Client schema enforced at completion (`claude`, `app-server`) | Where the client took the promise — `strict: true` on a tool or a `json_schema` format, or any Messages structured output — a forced tool's arguments or a `json_schema` answer outside the schema are refused with 502 instead of published; arguments or an answer that are not JSON are refused regardless. Conformance matrix §7 rows 8 and 10. |
| Streaming wire positions | `response.output_index` and Anthropic `content_block` indices are wire positions, allocated in the order items and blocks are emitted. Every item holds a distinct index, no block is stopped that was not started, and no delta is written to a block that was stopped: a tool call closes the open text block, so narration that resumes after the call opens a NEW text block. On `/v1/messages` the tool block closes when the turn's terminal frame confirms the call as finished (the vendor's finish event fixes the call's value at once; the signal that closes the block waits for the vendor to move on to a LATER output position — narration or another call's events carrying a higher `output_index`, at which point the call can no longer be the one a cut hits; a late frame for an earlier item is not that, and an event carrying no position proves nothing; the vendor's progress is retained — from frames that name no call, and from a tool event only once it is correlated, only at the call's accepted position, and only once the call can no longer fold into another — a `call_id` known or the call announced — so a duplicate frame for a known call mislabelled with a higher position is not progress (round 31; refused since round 45), and neither is an item-id half at a later position that then folds into the cut call (round 33; refused since round 45 — two accepted positions are two items) — so a call that learns its position, or finishes, after the vendor has moved past it is released on that frame — or for `response.completed`, since only those say the turn was not cut off inside it; round 26–30), so one block is open at a time — the narration that resumes after a call, and the next call, open with nothing else open. A backend that cannot say where a call's arguments end is the exception: its tool block stays open until the end of the turn, where the completed result still supplies whatever the stream was cut off before sending. A completed value may extend a call's finished fragment only while that finish signal has not gone out; once the block is closed the finished value stands on every path, and `/v1/messages` refuses a fragment that is not a JSON object on both (buffered 502; the bytes, then an in-band `error`, on the stream — round 28). The non-streaming `/v1/messages` body still carries one merged `text` block for a turn whose narration was split that way — the completed result flattens text into one string — so the two surfaces agree on content and can differ in block COUNT when text resumes after a tool call. The completed `response.output` array is ordered by those same positions, so `output[i]` is the item announced at `output_index: i`. | These indices are what SDK stream accumulators key on. Deriving a tool's index from its position among tools alone collided with the reasoning and message items when a turn both narrated and called a tool, and a tool block opening before the text block claimed an index the text block then reused. Assembling the completed array in a fixed order reintroduced the collision at the end of the stream, where a client reconciles what it accumulated against what the response says. |
| Streamed tool identity | A tool call is announced to the client only once the backend has supplied the `call_id` the client must echo back with the result. Arguments that arrive before it are held and delivered with the announcement — including argument deltas that carry no item id at all, which belong to the call that names their output position rather than to a call of their own. | Access gate | Off unless `authKey` is configured; with it set, every request except the CORS preflight and `CONNECT` (both answered with fixed, non-enumerating responses before the gate — 204 and 405 respectively, carrying nothing about what exists) must present the key as `Authorization: Bearer <key>` or `x-api-key: <key>` — including `GET` routes. The two are alternatives: presenting one valid credential authorizes the request even if the other header is present and wrong, and the same holds for repeated `x-api-key` lines — each physical header line is one candidate. A key may contain any characters, commas included: a single `x-api-key: a,b` is the one key `a,b`, not the two keys `a` and `b`. A bare `Authorization: <key>` without the Bearer scheme is not a credential. | Images `model` is a separate namespace | `modelSelection.honorRequestModel` does not apply to `/v1/images/*`. Those requests carry a direct-API image model name (`gpt-image-2` and its siblings, validated against the live list in the Images input spec), not a Codex model slug. | The Codex model that actually runs an image turn is `codexProxy.imageModel`, and the image model behind it is the backend's `gpt-image-2-codex` whatever name the request carried. `n` is an integer in 1..10 on every route; in JSON a numeric string is a type error, and only in multipart — where every field arrives as a string — do digits spell the integer. **Null is omission** for `n` and the other nullable-declared fields (`output_compression`, `partial_images`, the enums) — the direct API declares them `Optional[...]`. An empty STRING is different: it is a present value outside every enum and is 400, never silently dropped. Every member of a JSON `images` array must be an object and a valid reference — a malformed member is a 400 naming its index (`images[1]`), not silently filtered. Whether a body is multipart is decided by the media-type essence alone; a JSON request whose `content-type` parameters merely contain the words `multipart/form-data` is JSON. Within a multipart body, boundary bytes delimit only when the whole delimiter line matches (RFC 2046): at the start of a line, terminated by optional whitespace plus CRLF — or, for the close, `--` then optional whitespace then CRLF or end of body, with an epilogue allowed after. The same bytes inside a field value or an uploaded file are data, never a delimiter, prefixes included. The boundary parameter itself must satisfy the RFC grammar (1-70 characters from the boundary alphabet, not ending in a space; quoting allowed) — anything else is the boundary-required 400. Part headers are unfolded per RFC 822 before parsing, so a folded `Content-Disposition` keeps its parameters; duplicate singleton part headers resolve last-wins; an unterminated final part (no close delimiter) is dropped rather than guessed at. One whitespace rule holds throughout: **framing and parameter parsing strip ASCII OWS (space/tab) only** — a 0xA0 byte beside a boundary, a parameter name, a header name or a header value is a real byte that keeps the token malformed — while **blank-detection on decoded VALUES** (an empty prompt) uses Unicode whitespace, which is a statement about the value's content, not its framing. Further documented rejections, each a 400: `output_compression` below 100 requires `jpeg` or `webp` (`invalid_png_output_compression`); `background: transparent` requires a format carrying alpha; `input_fidelity` is edits-only (`unknown_parameter` on a generation). A present malformed `mask` is 400, never a silent unmasked edit. A response — streamed or not — carries at most `n` images, whatever the backend produces (streamed, the excess is skipped and the turn is still read to its terminal frame and judged — breaking out at the cap published a turn that failed after over-producing as a successful stream, round 48). `mask` exists only on edits — on a generation it is an unknown parameter, as its row states. |
